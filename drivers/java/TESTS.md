# Java driver tests (TC-DRV-JAVA-001…030)

Test names start with the TC id (`tc_drv_java_00x_…`, CLAUDE.md rule 1). The ids follow the ranges of
java-driver.md §9 / dotnet-driver.md §11 and match TC-DRV-NET-001…020 one to one (011…020 in the
order of the client-API list of dotnet-driver.md §11). All tests are in
`driver/src/test/java/io/rustegon/driver/` (mapping: `mapping/`, model compiled with the `processor`
subproject as annotation processor; robustness: `robustness/`). `./gradlew check` runs them on JDK 21
(`test`) and JDK 25 (`testJdk25`), DEC-020, and the JPMS smoke test of `samples/` on both. The packaging
checks 027/028 are not JUnit tests: `./gradlew validateCentralBundle` and `scripts/verify-reproducible.sh`.

Conformance files are read from `<repo>/drivers/conformance/`; `-Prustegon.conformanceDir=<dir>` (or
`RUSTEGON_CONFORMANCE_DIR`) points at another checkout. The tests that need them are skipped, with the
reason, while the suite is absent. Integration tests start `rustegond` from `RUSTEGON_BIN_DIR` (default
`<repo>/target/debug`, PD-072; build with `cargo build -p rustegond -p rustegon-cli`); they are skipped
without the binaries and fail instead under `CI=true`. The fixture runs `rustegon init --client-user
conf_x509` and `rustegond --set tls.client_cert=optional` so that the X.509 conformance test can log
in; the conformance runner creates its database per file, users per test, and one API key of the
administrator. The fake server of TC-DRV-JAVA-017/019 is the gRPC server of grpc-netty-shaded with
generic handlers over the generated service descriptors (no extra dependency). `StressTest` and `ReconnectTest` start their own
`rustegond` (`robustness/OwnedServer`: same binaries and skip rules, `rate_limit.enabled=false`, killable and
restartable on the same data directory and port) instead of the shared fixture.
